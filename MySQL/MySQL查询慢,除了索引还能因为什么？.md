# MySQL 查询慢，除了索引还能因为什么？

来源：@小白debug，约 5 分 50 秒。

除了索引选错，查询变慢主要还有两类原因：**连接数太小**，以及 **InnoDB Buffer Pool 太小**。

## 先看一条 SQL 怎么走完

应用（视频里用 Python）带着账号密码和 MySQL 建一条网络连接，由**连接管理**模块管这条连接。连上之后，SQL 经网络发到 MySQL，内部大致是：

1. **分析器**：先查语法。比如 `select` 少打了一个字母，这里就会被拦住。
2. **优化器**：按规则决定用哪个索引。
3. **执行器**：调用存储引擎的接口。真正读写数据的是存储引擎，现在最常用的是 **InnoDB**。

磁盘读写慢，所以 InnoDB 在内存里加了一层 **Buffer Pool**，里面既放行数据，也放索引。执行时按优化器选出的索引去找索引页；索引页不在 Buffer Pool 里，就从磁盘加载进来。再由索引页定位数据页；数据页也不在内存里，同样从磁盘读入。最后把一行行结果返回给客户端。

慢查询里最常见的一种，是**优化器选错了索引**，可以用 `EXPLAIN` 排查。视频说这块比较枯燥，细节放在配套文字笔记里，这一集只讲索引之外的限制。

## 原因一：连接数过小

MySQL 的连接管理模块，管的是客户端和 MySQL 之间的**长连接**。一条连接上，SQL 只能串行：后一条要等前一条执行完才能开始。

大量查询同时打过来时，后面的请求都堵在这条连接上。表现是：应用日志里某条 SQL 花了几分钟，把这条 SQL 单独拿出来执行却只有几毫秒。时间主要耗在**排队等前面的 SQL**，不是这条语句本身慢。多建几条连接，请求就能并发，后面的就不用等那么久。

连接数同时受数据库和客户端两边限制。

**数据库侧。** `max_connections` 默认是 100，最大可以到 16384。视频里的改法：

```sql
set global max_connections = 500;
```

**应用侧。** 库这边已经调大了却没效果，多半是 Java 或 Python 应用自己的连接数也太小。应用和 MySQL 之间是基于 TCP 的长连接，建立比较耗时，所以一般会维护一个**长连接池**：执行 SQL 时从池里取一条，用完放回去，下次复用。池的大小决定了应用这边真正能同时发出去的连接数。池太小，只改数据库的最大连接数没有用，要把连接池调大。

业务代码通常走 ORM，成熟的 ORM 都有连接池配置，按官方文档改即可。视频里的 SQLAlchemy 示例：

```python
from sqlalchemy import create_engine

engine = create_engine(
    'mysql地址',
    pool_size=10,  # 连接池大小
)
```

## 原因二：Buffer Pool 太小

InnoDB 的 Buffer Pool 用来缓存磁盘上的数据页和索引页。池越大，能放下的数据页越多，查询越容易直接命中内存，速度就越快。视频里把池调到约 512MB：

```sql
set global innodb_buffer_pool_size = 536870912;
```

池的大小正常、变慢另有原因时，再改它没有意义。要不要加大，看**缓存命中率**：

```sql
show status like 'Innodb_buffer_pool_%';
```

两个状态值：

- `Innodb_buffer_pool_read_requests`：读请求的次数
- `Innodb_buffer_pool_reads`：其中要从物理磁盘读数据的次数

命中率：

```text
命中率 = (1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests) × 100%
```

一般情况下应在 **99% 以上**。低于这个值，再考虑加大 Buffer Pool。视频建议把这个命中率放进监控，半夜变慢了，第二天也能对上原因。
